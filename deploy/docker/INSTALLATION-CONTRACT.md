本合同覆盖此前允许原地切换后端的设想；Mac 首先实现，其他宿主分别验收。

## 发行与入口

- 分别提供 Native 安装包与 Docker 安装包，安装器显式声明类型，不根据 Docker 是否存在自动选择。
- Docker 正式包包含宿主薄 CLI、审批桥、Dispatcher skills、Compose 模板、版本清单与镜像 digest；提供宿主安装脚本。Mac 首版宿主 Python 依赖必须预检并明示，不依赖开发 venv、源码或 Node。
- Docker 安装器检查 Docker/Compose 能力，建立受管安装目录和独立 Compose 项目，按 digest 获取镜像，完成 setup、服务就绪检查及 skill 安装。API/OAuth 延续原 CLI 模式，不统一要求人工登录。
- 两种安装都只提供一个日常 `agentbc` 入口；Docker 将业务命令路由到容器，setup、安装维护与审批桥在宿主管理。不得另留可并行使用的正式 Native 入口。
- `agentbc --version`、doctor、setup 摘要及安装回执明确显示 `installation_type=native|docker`、版本和安装位置；Docker 额外显示镜像 digest、Compose 项目及服务状态，不显示凭据。
- Docker setup 保持英文，WebUI 为主要监控方式，保存固定端口和后台偏好并告知访问地址；私有 token 仅在启动链接提供，不进入安装回执。

## 双向互斥

互斥覆盖同一宿主当前用户的正式安装，不局限于目标目录或当前 PATH；共享系统安装若对当前用户可见同样阻止冲突。不能声称可枚举其他用户的私有安装。

| 已有状态 | 安装 Native | 安装 Docker |
| --- | --- | --- |
| 无正式安装 | 允许 | 允许 |
| Native（含停止状态） | 走同类型升级规则 | 失败，要求先卸载 Native |
| Docker（含停止状态） | 失败，要求先卸载 Docker | 走同类型升级规则 |
| 安装中、卸载未完成、归属不明或多实例冲突 | 失败，先诊断修复 | 失败，先诊断修复 |
| 仅保留记录、报告、产物或未运行的镜像缓存 | 允许 | 允许 |

- 不提供跨类型 `--force`、静默覆盖、自动卸载或 backend 原地切换。改变 prefix、PATH、关闭 Runner 或停止 Docker 均不能解除互斥。
- 原生本地包、URL 安装、更新入口、Docker 安装入口及受支持的恢复安装入口共用检查；低层手工 pip/直接复制文件不宣称可被完全阻止，但已发现的旧版或非受管 CLI 必须阻止正式安装。
- 检查结合统一安装登记、已知历史目录、PATH 全部候选、受管服务/登录项、skill 安装来源及 Docker 安装项目身份；不能只查 `which agentbc`、PID 或容器是否运行。
- 单独源码 checkout、未接管正式入口/skill 的测试 fixture 不当作正式安装。现有隔离开发入口不是正式安装验收证据，也不提供面向用户的跳过互斥开关。
- Docker 已登记但 daemon 不可达时仍视为已安装；需要检查未登记 Docker 残留却无法连接时返回“无法完成安装检查”，不能当作不存在。

## 登记与失败处理

使用当前用户固定位置的共享安装登记与跨类型安装锁，不随 prefix 改变。登记最小字段：schema、installation_id、type、version、路径、受管资源身份及 installing/installed/uninstalling/repair_required 状态；禁止存 token 或 Executor 凭据。

安装先预检，再取得锁并重新检查，之后才写配置、skill、服务和命令入口。两个安装器并发只能有一个取得安装资格。旧版没有登记时先识别真实安装，不能因缺少标记放行。

失败仅回滚本次创建且身份匹配的资源；无法完成回滚保留 repair_required 和诊断，不提前释放安装资格。身份验证不能只用容器名称或 PID。既有用户修改的 skill 不得强行覆盖。

## 跨类型切换：卸载，再重新安装

1. 停止接收新任务，检查运行中、等待审批和未关闭租约；有未结业务时拒绝卸载，先由用户完成或通过既有业务命令处理。不得为切换自动取消任务。
2. 备份配置和需保留的任务、报告、产物；保留凭据的方式需明确且保持用户私有权限。备份不等于目标版本已经导入成功。
3. 使用当前类型的卸载流程，清理自有 Runner、WebUI、审批桥、登录项、正式 CLI 和受管 skills；Docker 仅清理该 installation_id 对应资源，不卸载 Docker Desktop，不影响其他项目。数据删除遵循明确选择，禁止默认 `down -v`。
4. 核实可执行入口、服务与安装资源已清除后才解除登记。部分卸载失败仍阻止另一类型安装。保留数据与镜像缓存不占安装资格。
5. 运行目标类型安装器并重新 setup；保留数据必须显式导入/挂接并验证路径与格式，不能静默共用活动工作区。导入已有 API/OAuth 配置不改变 provider/model 或权限策略。
6. 验证唯一 Runner、CLI/skill 派发接收、审批、报告及 WebUI。切回同样执行“卸载 Docker → 安装 Native”；不能恢复第二个并存实例作为回退。

同类型升级可事务回滚；跨类型回退仍受卸载重装规则约束。卸载当前会删除配置的旧实现需要先补保留/导出流程，不能直接当作无损迁移。

## 分步实施与验收

1. **INSTALL-01**：统一身份、发现与锁；双向冲突、旧版无登记、非 PATH 安装、停止状态、并发、陈旧登记、Docker 不可达测试。冲突失败必须非零退出且既有文件和服务不变。
2. **INSTALL-02**：Native 所有发行入口接入守卫，Docker 正式包及 setup 接通；验证同类型升级、英文提示、固定端口、安装身份与无源码运行。
3. **INSTALL-03**：两类卸载、备份保留和失败恢复；验证未结任务阻止卸载、修改过的 skill、卸载中断、重试和数据未丢失。
4. **INSTALL-04**：隔离环境执行 Native → 冲突拒绝 → 卸载 → Docker → 冲突拒绝 → 卸载 → Native；每一步核对入口、服务、登记、数据与退出码。
5. **INSTALL-05**：最终候选同镜像四 Executor 和真实 Dispatcher、审批、WebUI 人工验收后，才安排用户本机正式卸载重装。OpenCode 原生审批继续归 1.06a，不作为本期门槛。

实施前不得把现有 docker_host.install 的“空 prefix 检查”报告成双向互斥已实现。测试和文档完成也不能代替真实切换人工验收。
